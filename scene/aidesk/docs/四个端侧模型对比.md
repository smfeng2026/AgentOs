# **四款端侧小模型：架构特点、优缺点与产品适配分析**

现在确定的四个模型是：

1. MNN-Pocket-0.3B
2. LFM2.5-350M
3. MiniCPM4-0.5B
4. Qwen3-0.6B

这四个模型其实很有研究价值，因为它们并不只是参数量不同，而是代表了三种值得比较的技术思路：

- **传统 Transformer 的端侧协同优化**：MNN-Pocket、Qwen3、MiniCPM4。
- **混合卷积与注意力架构**：LFM2.5。
- **面向端侧的系统性优化**：MiniCPM4、MNN-Pocket。

我先给出一个重要判断：

**如果你的研究重点是 Android/iPhone 上的综合 AI 能力，那么这四款模型最大的区别，在于它们如何平衡模型表达能力、KV Cache、计算量、内存访问和推理速度。**

这比简单比较 300M、350M、500M、600M 更值得研究。

## **二、逐个深入分析**

### **1. MNN-Pocket-0.3B：为移动端效率做协同优化的 Transformer**

[MNN-LLM Android App网页版入口、使用教程-太平洋科技AI产品库](https://images.openai.com/static-rsc-4/r6RFByeqCw_G4aJW9P39zTo_YXPE1862jTuZAwKO6Uet4hfP29lXM_UfwNV2G74IDawM_4x9Z4_2l24a4zc6FlLQ8Yy4gEwZDLXRIa2DUk2gw2vzwD6Y4LOHEsSN0nnGENezMMVPWMYsjxptt3_Auf0ReqrgkFgn2tUqK6nlFoU?purpose=inline)

**MNN-Pocket-0.3B**

产品主力候选

约 300M 参数 · INT4 QAT

**架构特点**

它采用标准 Decoder-only Transformer，核心结构是：

| 配置               | 数值      |
| ---------------- | ------- |
| Transformer 层数   | 28      |
| Hidden Size      | 896     |
| Attention Heads  | 14      |
| KV Heads         | 2       |
| Head Dimension   | 64      |
| FFN Intermediate | 2560    |
| 激活函数             | SiLU    |
| Vocabulary       | 65,536  |
| 上下文              | 32K（部署） |

这里最值得关注的是 GQA。

它使用 14 个 Query Heads，但只有 2 个 Key/Value Heads。

普通 MHA 中，每个注意力头都有自己的 KV；GQA 则让多个 Query Heads 共享 KV。

这能够减少 KV Cache 和内存访问成本。

此外，它还有两个非常值得研究的端侧优化：

**第一：INT4 QAT 量化。**

不是简单训练完之后再做 INT4 量化，而是在训练阶段就考虑低精度部署。

官方公布：

- BF16 模型平均分：50.00。
- INT4 模型平均分：49.59。
- INT4 权重约 171MB，完整模型文件约 173MB。

这意味着它的量化精度损失在官方 11 项评测中比较小。

[image](https://www.google.com/s2/favicons?domain=https://huggingface.co\&sz=32)

taobao-mnn/MNN-Pocket-0.3B at main+1



**第二：专门针对 MNN 推理引擎优化。**

MNN-Pocket 不只是一个小型 Transformer，而是模型权重、量化方案和推理引擎协同设计的产物。

**优点**

- 参数量小，模型体积优势明显。
- GQA 只有 2 个 KV Heads，KV Cache 压力相对小。
- 中文和英文能力有明确优化目标。
- 已有 Android/iOS 的 MNN 部署版本。
- QAT INT4 版本适合移动端资源预算。

**缺点**

- 传统 Transformer 仍然需要维护随上下文增长的 KV Cache。
- 长上下文并不意味着长文本理解能力一定强。
- 与 MNN Runtime 的深度绑定会增加跨推理框架的比较成本。
- 300M 参数对复杂推理仍有明显能力上限。

还有一个值得单独研究的技术分支：

MNN-Pocket 另外提供 `MNN-Pocket-0.3B-Dec`，它不是普通的自回归生成模型，而是通过 LoRA Adapter 和 Pointer Head 实现非自回归决策，一次前向推理完成决策输出。

[image](https://www.google.com/s2/favicons?domain=https://huggingface.co\&sz=32)

taobao-mnn/MNN-Pocket-0.3B at main



我建议暂时不把 Dec 版本混入四模型主实验，因为它和另外三个模型的输出机制不同。但可以作为后续研究方向。

**我的评价：** 最适合做 Android/iOS 主力产品原型，也是本次研究的核心目标模型。

### **2. LFM2.5-350M：用混合架构降低端侧计算成本**

[Liquid AI: Build efficient general-purpose AI at every scale.](https://images.openai.com/static-rsc-4/wFryctldf1mudErIOCmBWbHj7s3OZGjFXpt5cKXKkcFtt9E3HzkCQit3-LCrtGd_v32O9vKcTqwfYv5urIngJz6vsCwIRYcwOesn0qUvPO3SXzGP-LRWXmSR7_mbzlkziZ3_24wEAV-jQwJE2TiephRhKOMQ5_-pWry4QIS2VhA?purpose=inline)

**LFM2.5-350M**

最有架构研究价值

约 350M 参数 · 混合架构

这是四款模型中最特殊的一款。

它不是简单地把 Transformer 缩小，而是采用了卷积模块和注意力模块混合的架构。

**架构特点**

官方配置：

| 配置         | 数值     |
| ---------- | ------ |
| 参数量        | 350M   |
| 总层数        | 16     |
| 双门控卷积模块    | 10     |
| GQA 注意力模块  | 6      |
| Vocabulary | 65,536 |
| 上下文        | 32K    |

其中：

- 卷积模块负责序列信息的局部混合。
- 注意力模块负责更灵活的全局信息交互。
- 双门控机制用于控制信息流动。

它的设计思想是：

**并不是每一层都需要完整的 Self-Attention。**

对于大量局部依赖的序列计算，可以采用卷积结构；对于需要跨位置建立关联的部分，再使用注意力机制。

这能够减少部分注意力计算和 KV Cache 的需求。

与传统 Transformer 相比，它有机会获得更低的推理内存成本和更快的 Decode 速度。

官方公布的特定测试数据：

- AMD CPU：313 tokens/s。
- Snapdragon Gen4：188 tokens/s。
- 运行内存低于 1GB。

这些是 Liquid AI 的测试结果，不是与你的其他三款模型在统一手机环境下的比较成绩。

[image](https://www.google.com/s2/favicons?domain=https://huggingface.co\&sz=32)

Hugging Face+1



**优点**

1. 卷积模块不需要像标准注意力那样维护完整的历史 KV Cache。
2. 只有部分层使用 GQA，降低注意力模块的计算负担。
3. 参数规模与 MNN-Pocket 接近，比较有价值。
4. 提供 GGUF、ONNX 等部署格式。
5. 官方明确针对信息抽取、结构化输出、工具使用进行推荐。

**缺点**

1. 混合架构对推理引擎的算子支持提出更高要求。
2. 卷积的局部建模与注意力的全局建模之间存在能力权衡。
3. 如果业务依赖复杂的远距离指代和跨轮关联，需要重点测试。
4. 它的知识密集型任务和编程能力并非官方推荐方向。
5. 中文虽然在支持语言之列，但不能据此认定中文业务表现一定优于其他模型。

这里有一个很重要的研究点：

假设你的数据集包含大量这样的任务：

> 用户前面提到一个事情，过了几轮又说“把刚才那个时间改一下”。

这种任务需要跨轮次、跨位置的信息关联。

那么 LFM2.5 是否能通过混合架构，在较低内存开销下保持足够的上下文理解能力？

这是非常值得验证的。

**我的评价：** 四款模型中最适合用来研究不同序列建模架构对手机端综合能力的影响。

### **3. MiniCPM4-0.5B：通过模型、算法、数据和推理系统协同优化**

[MiniCPM-V 2.0: An Efficient End-side MLLM with Strong OCR and Understanding Capabilities](https://images.openai.com/static-rsc-4/bgRAH1vtvwJ5RQ1o9W3dZsDKQrm-ex3gZlILvSOw2a7TjDaKlOLGcB0CyyffKRTU9Wnbkzc4coo-_d8AbuM3kFtdJ96ixexlzAKTepmn7uve55eHH3lc9eEcxBVIIvcCiakffdWbESh4KKDcj-eZuqwAUWzgikXACqd3pGkHfag?purpose=inline)

**MiniCPM4-0.5B**

端侧效率对照

约 500M 参数 · GQA Transformer

这里我要特别纠正一个容易产生的误解：

MiniCPM4-0.5B 并不是像 LFM2.5 那样的卷积与注意力混合架构。

它本身仍然是 Decoder-only Transformer。

它的核心创新更多体现在端侧优化体系上。

**架构特点**

从官方配置文件可以看到：

| 配置               | 数值     |
| ---------------- | ------ |
| Transformer 层数   | 24     |
| Hidden Size      | 1024   |
| Attention Heads  | 16     |
| KV Heads         | 2      |
| Head Dimension   | 64     |
| FFN Intermediate | 4096   |
| Vocabulary       | 73,448 |
| 上下文              | 32K    |

其中最值得关注的是：

- GQA：16 个 Query Heads 共享 2 个 KV Heads。
- LongRoPE：支持上下文位置扩展。
- SiLU：作为 FFN 激活函数。

它的 GQA 结构与 MNN-Pocket 有一定相似性，但 Hidden Size、层数和 FFN 规模都不同。

[image](https://www.google.com/s2/favicons?domain=https://huggingface.co\&sz=32)

openbmb/MiniCPM4-0.5B at main+1



**MiniCPM4 的真正创新在哪里？**

我认为主要是四个方面：

**① 模型架构优化**

InfLLM v2 可训练稀疏注意力技术，目标是降低长文本注意力计算开销。

**② 量化优化**

BitCPM 三值量化技术，将权重表示压缩到三种离散值。

**③ 训练算法优化**

Model Wind Tunnel 2.0、FP8 训练和 Multi-token Prediction。

**④ 推理系统优化**

CPM.cu 和 ArkInfer，分别侧重推理效率和跨平台部署。

[image](https://www.google.com/s2/favicons?domain=https://huggingface.co\&sz=32)

Hugging Face+1

需要注意：MiniCPM4-0.5B 的模型配置最大上下文是 32K。官方关于 InfLLM v2 的低于 5% 注意力计算量描述，主要针对 128K 长文本处理技术，不能直接理解成这个 0.5B 模型在手机上的所有推理都只需要 5% 的计算量。

**优点**

- 2 个 KV Heads，具有较好的 KV Cache 规模优势。
- 端侧优化不只依靠量化，而是覆盖训练和推理系统。
- 有专门的极小模型版本。
- 中文和英文均在模型卡覆盖范围内。
- 有专门的三值量化研究路线。

**缺点**

- 模型本身仍然是 Transformer，普通短上下文场景未必能充分体现稀疏注意力的优势。
- 官方 ArkInfer、CPM.cu 的跨平台能力不等于已经证明 Android/iOS 两端都能无障碍部署。
- 需要 `trust_remote_code=True` 的 Transformers 路线，意味着模型代码兼容性和维护成本值得关注。
- 0.5B 模型的能力上限依然有限。

**我的评价：** 它与 MNN-Pocket 非常值得比较，因为两者都以端侧效率为目标，但优化手段不同。

MNN-Pocket 更突出模型与 MNN 推理引擎的协同及 INT4 QAT；MiniCPM4 更突出系统性的架构、训练和推理优化。

这两个模型之间的比较很有研究价值。

### **4. Qwen3-0.6B：传统 Transformer 路线中的综合能力参考**

[全新开源通义千问Qwen3模型系列特性与能力详解-开发者社区-阿里云](https://images.openai.com/static-rsc-4/d1KHIhckNcXxXUlPAn4KkYugbmM1bKFkYs6TGQx57KFj6gw0w4dESo5t8QbxdgpEu8ZoQphEYkzArwGfOaFFHNeq5wi-w9GNMz__YWo635uBS5K4xF8ZdqTbL9UmTncmlotylqEvA1c7LpGNFylRzFy7SW-UN9jbRlaVhqTLE6w?purpose=inline)

**Qwen3-0.6B**

综合能力对照

约 600M 参数 · Thinking / Non-thinking

Qwen3 的架构反而比较传统。

它没有采用 LFM2.5 的混合卷积结构，也没有像 MNN-Pocket 那样深度绑定专门的移动端 INT4 推理方案。

它采用标准 Decoder-only Transformer + GQA。

**架构特点**

| 配置               | 数值      |
| ---------------- | ------- |
| Transformer 层数   | 28      |
| Hidden Size      | 1024    |
| Attention Heads  | 16      |
| KV Heads         | 8       |
| FFN Intermediate | 3072    |
| Vocabulary       | 151,936 |
| 上下文              | 32K     |

最值得注意的是它的 8 个 KV Heads。

对比其他三个模型：

- MNN-Pocket：2 个 KV Heads。
- LFM2.5：只有 6 个 GQA 注意力模块，不能简单按 2 个 KV Heads 与其他模型直接等价比较。
- MiniCPM4：2 个 KV Heads。
- Qwen3：8 个 KV Heads。

这意味着 Qwen3 在相同层数、相同上下文长度和精度下，KV Cache 的规模可能明显更大。

但需要强调，实际内存还取决于 Head Dimension、数据精度和缓存实现。

**Qwen3 有什么特殊优势？**

它支持两种工作模式：

1. Thinking：复杂推理模式。
2. Non-thinking：快速通用对话模式。

对于你的产品，建议主要研究 Non-thinking。

Thinking 可以作为额外能力实验。

它在训练方面重点加强了：

- 推理能力。
- 指令遵循。
- Agent 能力。
- 多轮对话。
- 多语言能力。

官方支持 100 多种语言和方言。

[image](https://www.google.com/s2/favicons?domain=https://huggingface.co\&sz=32)

Hugging Face+1



**优点**

- 模型参数量相对最大。
- 中文及多语言能力值得作为综合基线。
- Thinking / Non-thinking 可以研究不同推理策略。
- 工具调用和 Agent 能力有明确训练支持。
- 模型生态成熟，部署和量化工具较丰富。

**缺点**

- 8 个 KV Heads 相对其他两款 GQA Transformer 更容易增加 KV Cache 压力。
- 词表达到 151,936，Embedding 和输出层的参数成本不容忽视。
- 默认 Thinking 模式可能产生额外延迟和 Token 消耗。
- 并非专门针对 Android/iPhone 协同优化。
- 更大的模型不代表手机端综合体验一定更好。

**我的评价：** 它最适合作为综合语言能力参考，尤其是多轮理解、任务判断、复杂指令和轻量 Agent 场景。

### **一个值得特别关注的细节：KV Cache**

我们以 BF16 KV Cache、上下文长度 4096 Token 为例，做一个理论估算。

计算公式：

\\[ M\_{KV}=2\times L\times H\_{KV}\times D\_{head} \times T\times B \\]

其中：

- \\(L\\)：注意力层数。
- \\(H\_{KV}\\)：KV Heads。
- \\(D\_{head}\\)：Head Dimension。
- \\(T\\)：上下文 Token 数。
- \\(B\\)：每个元素字节数，BF16 为 2。

4K 上下文下的理论 KV Cache

BF16，按官方层数和注意力配置估算；不含运行时开销。LFM2.5 因混合架构不纳入该简单公式比较。

0 MiB150 MiB300 MiB450 MiB600 MiBMNN-PocketMiniCPM4Qwen3

这组计算有很强的参考价值：

- MNN-Pocket：约 56MiB。
- MiniCPM4：约 48MiB。
- Qwen3：约 448MiB。

这里没有计算模型权重、临时张量和运行时开销，也没有考虑 KV Cache 量化。

这说明一个问题：

**Qwen3 虽然只有 0.6B 参数，但其 KV Cache 设计并不像另外两个 GQA Transformer 那样节省。**

LFM2.5 则因为混合架构，不能简单套用完整 Transformer 的 KV Cache 公式，需要进一步测量其实际状态缓存。

| KV Cache 效率 | 高          | 架构有优势  | 高        | 相对较高开销 |
| 量化方案        | INT4 QAT   | GGUF 等 | BitCPM 等 | GGUF 等 |
| 手机部署成熟度     | 较高         | 需要验证   | 需要验证     | 需要验证   |

这里的能力评价是根据架构和官方定位提出的研究假设，并非你的数据集上的实测结果。

### **我的综合判断**

最适合主力产品验证

**MNN-Pocket-0.3B**

体积、中文优化、端侧部署和量化方案之间的平衡比较好。

最值得研究架构差异

**LFM2.5-350M**

可以验证混合卷积与注意力机制在手机端的实际价值。

最值得研究端侧系统优化

**MiniCPM4-0.5B**

可以研究稀疏注意力、量化和推理系统协同的实际效果。

最值得研究综合能力

**Qwen3-0.6B**

可以观察更大参数规模和推理训练对多轮交互、任务判断的贡献。

## **五、我认为四款模型最值得研究的四个问题**

这部分我建议直接作为后续技术研究的主线。

| 研究方向     | 对比模型                     | 要回答的问题                 |
| -------- | ------------------------ | ---------------------- |
| 架构差异     | MNN-Pocket vs LFM2.5     | 混合架构能否在较低资源下保持综合能力？    |
| 端侧优化     | MNN-Pocket vs MiniCPM4   | 不同系统优化路线谁的实际效率更好？      |
| 参数规模     | MNN-Pocket vs Qwen3      | 参数增加一倍，业务能力是否有显著提升？    |
| KV Cache | 三款 Transformer vs LFM2.5 | 不同序列建模方式对长上下文内存的影响有多大？ |

还有一个值得单独研究的问题：

**模型参数量和推理速度之间是否存在明显的非线性关系？**

例如，Qwen3 参数更多，但如果它的 KV Cache、词表输出层和内存访问成本更高，实际手机体验未必比 MNN-Pocket 更好。

这正是端侧模型研究与普通模型 Benchmark 研究的区别。

## **六、我建议下一步的实验设计**

我不建议一开始就对四款模型全部进行微调。

建议分成三个阶段：

1. **阶段一：原始模型架构和能力基线**
   - 统一业务测试集。
   - 统一任务 Prompt。
   - 统一输出 Schema。
   - 记录准确率、模型体积和内存。
   - 分析不同架构的错误类型。

   目的：确定各模型的原始能力边界。
2. **阶段二：统一业务数据集微调**
   - 使用相同训练集。
   - 采用适合各模型的微调方法。
   - 记录微调前后准确率变化。
   - 观察不同架构的领域适应能力。

   目的：确定谁最容易被你的数据集优化。
3. **阶段三：Android/iOS 真机部署**
   - 对比不同量化方案。
   - 测试 CPU/GPU/Metal 等后端。
   - 记录 TTFT、Decode、峰值内存。
   - 记录连续运行发热和功耗。
   - 验证跨平台结果是否一致。

   目的：确定真正适合产品的模型。

## **七、我还有一个重要建议：把 MNN-Pocket 的 Dec 版本作为第五个专项实验**

前面提到，MNN-Pocket 有一个非常特殊的版本：

`MNN-Pocket-0.3B-Dec`

它不是普通的自回归语言模型，而是非自回归决策模型。

如果你的场景数据集包含大量：

- 用户意图分类；
- 固定动作选择；
- 任务类型判断；
- 参数槽位提取；
- 有限候选项决策；

那么这个版本可能比普通生成模型更值得研究。

我建议把它作为独立的专项实验，不纳入四个通用生成模型的直接排名。

## **最后，我想确认一个对后续架构分析很关键的问题**

你现在研究的端侧 AI 产品，更偏向哪一种能力？

**自然语言交互型**

用户随意表达，模型理解、回答、总结和持续对话。

**任务执行型**

用户发出指令，模型识别意图、提取参数、选择动作并调用手机功能。

**混合型**

既要自然语言对话，也要理解和执行用户任务。

**智能决策型**

更关注多轮上下文、状态判断、任务选择和流程决策。

确定产品能力方向

因为这会直接影响一个重要判断：

**我们到底应该优先选择语言理解能力更强的 Transformer，还是更高效的混合架构，或者针对任务决策专门优化的模型。**

这也是我认为四款模型最值得深入研究的地方。
