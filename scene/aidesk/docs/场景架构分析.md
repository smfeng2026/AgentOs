你这次提出的六个问题非常关键，而且我认为你指出了上一版架构中一个需要纠正的地方：

**不能先把用户真实操作浓缩成几个抽象事件，再让模型推测用户意图。应该先尽可能准确地采集用户操作中的原始业务信息，保留上下文和证据，然后再逐层抽象、关联和推理。**

例如：

```
{"event": "查看高铁票", "time": "09:00"}
```

这个数据对 AI 桌面来说远远不够。

因为它丢失了：

- 查询了哪几个出发地和目的地？
- 查询的是哪一天？
- 查询了哪些时间段？
- 查询的是哪些车次？
- 用户是搜索车票，还是查看已购买订单？
- 是否已经支付？
- 用户有没有修改订单？
- 多次查询之间是什么关系？

这些信息恰恰决定了系统能否识别真实意图。

我重新梳理一下，我认为你的 AI 桌面应该采用一套更严谨的技术架构：

**应用感知 → 页面路由识别 → 采集策略决策 → 控件树/页面语义采集 → 结构化业务数据 → 事件关联 → 意图推理 → 推送决策。**

这次我会重点从 OpenHarmony 系统实现角度分析，而不是单纯从模型角度分析。

# **一、应用本身是不是就代表一种场景命中？**

你的理解基本正确，但需要区分两个概念：

- 应用命中（App Match）
- 场景命中（Scenario Match）

应用本身可以作为场景识别的第一层信号，但不能直接等同于场景。

例如：

| 应用     | 可能对应的场景 | 实际操作目的       |
| ------ | ------- | ------------ |
| 铁路购票应用 | 出行      | 搜索车票、查看订单、退票 |
| 地图应用   | 出行、导航   | 搜索地点、导航、查看路线 |
| 酒店应用   | 旅行、商务出差 | 搜索酒店、查看订单    |
| 邮件应用   | 工作、沟通   | 阅读邮件、处理通知    |
| 电商应用   | 购物      | 浏览商品、下单、售后   |
| 日历应用   | 工作、生活   | 创建会议、查看日程    |

同一个应用可能对应多个场景。

因此，我建议建立三级判断机制。

## **1. 第一级：根据应用包名进行场景初筛**

这是最轻量的判断，不需要 AI 模型。

通过包名维护一个应用分类库：

```
{
  "bundleName": "com.example.railway",
  "appCategory": "TRAVEL",
  "sceneCandidates": [
    "TRAIN_TRAVEL",
    "BUSINESS_TRIP",
    "PERSONAL_TRAVEL"
  ],
  "collectionPolicy": "ENHANCED_CANDIDATE"
}
```

建议维护以下信息：

| 字段                   | 作用     |
| -------------------- | ------ |
| bundleName           | 应用唯一标识 |
| appCategory          | 应用分类   |
| sceneCandidates      | 潜在场景   |
| businessCapabilities | 业务能力   |
| collectionLevel      | 默认采集等级 |
| privacyLevel         | 数据敏感等级 |

这里有一个重要设计：

不要只维护一个包名对应一个场景，而要维护一个包名对应多个业务能力。

例如铁路购票应用：

```
铁路购票应用
  ├── 车票搜索
  ├── 车票列表
  ├── 订单详情
  ├── 支付
  ├── 退票
  └── 改签
```

因为这些页面的业务意义完全不同。

## **2. 第二级：应用内页面识别**

进入应用之后，进一步识别用户当前处于什么业务页面。

例如：

[বসন্ত উত্সবকে সামনে রেখে চীনে ১২৩০৬ রেলওয়ে মোবাইল অ্যাপের বিশেষ পরিষেবা](https://images.openai.com/static-rsc-4/v0pZestsRml5H1y90T4TtKGn4q2uxt7QmPcSWUxQIMP1jurJI__YKYQYuNCDOqkz7ZRJN0j4cz9HP6swkMgQlO3zv0JU2J45AI5_P0hQrsWyJPAPZz4Bz3xwjOv3Fkd30ZTA6QuoJ_vXBPJ-i2B2gSB0Qm4qY4bpjTMY0Bi6DeE?purpose=inline)

**铁路购票应用**

**车票搜索页**

用户正在查询出行方案

L2 候选

**车次列表页**

用户正在比较具体车次

L2

**订单详情页**

用户可能已经购买车票

L3

**个人中心页**

用户正在查看个人信息

通常 L1

这里的 L2、L3 是采集策略等级，不是页面重要程度的绝对排序。比如订单详情可能涉及高度敏感的个人信息，即使业务价值高，也必须经过更严格的权限和数据最小化控制。

## **3. 第三级：结合行为序列识别真正场景**

例如：

```
打开铁路购票应用
    ↓
搜索北京 → 上海
    ↓
修改日期
    ↓
查询北京 → 南京
    ↓
返回上海车次列表
    ↓
打开订单详情
```

这里不能简单判断为：

用户正在出差。

因为用户可能在比较多个出行方案，也可能是帮别人购票。

但是系统已经可以判断：

- 用户正在进行铁路出行相关活动。
- 用户关注北京到上海、北京到南京两个路线。
- 用户进行了多次查询。
- 用户可能正在比较出行方案。
- 是否已经完成购买，需要进一步查看订单状态。

**所以我的结论是：包名负责发现候选场景，页面路由负责识别业务动作，行为序列负责推测真实意图。**

第一层完全可以使用规则，不需要决策模型。

# **二、用户操作频繁，涉及多个页面路由，哪些页面需要采集？**

这是你整个采集系统最核心的工程问题。

我认为不能采用简单的白名单机制，也不能所有页面都采集。

建议采用：

**页面业务价值 + 用户操作类型 + 控件语义 + 上下文关联 + 数据敏感等级**

五个维度共同决定采集策略。

## **1. 首先建立页面业务类型分类**

不要直接按页面 URL 或路由名称决定采集等级。

因为不同应用的路由命名不统一，有些页面甚至没有可获取的路由名称。

应该建立统一的页面业务类型。

| 页面业务类型 | 示例        | 主要采集目标        |
| ------ | --------- | ------------- |
| 首页/导航页 | 应用首页      | 通常只记录进入事件     |
| 搜索输入页  | 车票搜索      | 用户输入的关键词、查询条件 |
| 搜索结果页  | 车次列表      | 具体候选结果        |
| 详情页    | 车票详情      | 用户关注的对象和属性    |
| 交易页    | 支付页面      | 交易状态，需严格控制    |
| 订单页    | 订单详情      | 已购买对象、时间、状态   |
| 表单页    | 创建会议、填写信息 | 用户填写的业务字段     |
| 内容浏览页  | 新闻、文章     | 浏览对象、主题       |
| 设置页    | 系统或应用设置   | 通常不需要深度采集     |

这一步的目的，是把不同应用的页面映射到统一的业务语义上。

## **2. 轻量采集和深度采集应该怎么界定？**

我建议你重新定义三个采集级别。

**L1：轻量采集**

低成本

采集页面和操作的基本结构，不深入解析全部业务内容。

例如：

- 当前应用包名。
- 页面类型。
- 页面路由（如果可获得）。
- 用户操作类型。
- 页面跳转关系。
- 关键控件的语义标签。

**L2：业务字段采集**

重点

提取当前页面真正有业务价值的字段。

例如搜索页：

- 出发地。
- 目的地。
- 出发日期。
- 搜索条件。

订单页：

- 订单状态。
- 出发地。
- 目的地。
- 车次。
- 出发时间。

**L3：深度语义采集**

按需触发

对页面内容进行跨控件、跨页面和跨事件语义理解。

例如：

- 用户为什么反复修改出发日期？
- 为什么比较两个目的地？
- 是否在为同一个会议安排出行？
- 已购买的车票是否与会议时间冲突？

这里特别强调：

**L2 和 L3 不是简单的数据量大小区别，而是结构化字段提取与上下文语义推理的区别。**

L2 甚至可能比 L3 提取更多原始字段，但不一定需要运行 LLM。

## **3. 以车票搜索为例，具体应该采集什么？**

假设用户进行以下操作：

```
09:00 打开铁路购票应用
09:01 搜索北京 → 上海
09:03 查看车次列表
09:05 修改日期为12月3日
09:07 查看北京 → 南京
09:10 返回北京 → 上海
09:12 查看G101次列车
09:15 返回搜索结果
```

我建议这样处理：

| 用户操作    | 页面类型  | 采集内容          | 等级 |
| ------- | ----- | ------------- | -- |
| 打开应用    | 首页    | 包名、页面类型       | L1 |
| 输入北京、上海 | 搜索页   | 出发地、目的地       | L2 |
| 选择12月3日 | 搜索页   | 日期变化          | L2 |
| 查询车次    | 搜索结果页 | 查询条件、结果摘要     | L2 |
| 查看北京、南京 | 搜索页   | 新的查询条件        | L2 |
| 返回上海    | 搜索页   | 查询条件恢复        | L2 |
| 查看G101  | 车次详情页 | 车次、时间、票价等必要字段 | L2 |
| 反复比较    | 跨页面行为 | 关联和意图分析       | L3 |

这样就能保留真实的用户操作，而不是仅仅记录一个抽象的「查询车票」事件。

## **三、轻量采集是不是直接获取控件树？深度采集是不是使用页面理解？**

你的思路是对的，而且我认为这是最值得利用 HarmonyOS 系统能力的地方。

但我建议稍微调整一下定义：

**控件树是页面结构和内容的基础数据来源；页面理解是对控件树、页面视觉信息和上下文进行语义解释的增强能力。**

两者不是相互替代的关系。

### **1. 轻量采集：优先使用控件树，不调用大模型**

假设用户打开车票搜索页面：

[中国の電車チケット予約方法：12306とTrip.comを徹底比較 | WaysChina](https://images.openai.com/static-rsc-4/ULWplVXkgXOsBoXPmPTmGRWtvy0T_-WnKGYFPqLVPUOvbaKbBl2gHRkIFOzD5fUVqNO8xrOI4Juz12F9qwipg8xHa9jFZ53srkrMS9rM4-Fq91PR9-B318k6yjbLwkPEAj_ud3BDlrQTsNiymixfrIMm4mv5CrHtv10QSmpaLJI?purpose=inline)

[wayschina.com](https://www.wayschina.com/ja/articles/how-to-book-train-tickets?utm_source=chatgpt.com)

页面中可能有：

- 出发站：北京南
- 到达站：上海虹桥
- 出发日期：12月3日
- 学生票：关闭
- 查询按钮

如果控件树能提供这些信息，那么完全没有必要调用 LLM 或页面理解模型。

可以直接解析：

```
{
  "page_type": "TRAIN_SEARCH",
  "controls": [
    {
      "role": "Text",
      "semantic": "departure_station",
      "value": "北京南"

```

注意，这只是目标数据结构示例，并不意味着所有第三方应用的控件树都能直接提供这样的语义标签。

实际可能拿到的是：

- 控件类型。
- 控件文本。
- Accessibility Label。
- 控件层级。
- 是否可点击。
- 是否可编辑。
- 部分状态信息。

系统需要通过页面模板和控件语义映射，将它们转换成业务字段。

### **2. 轻量采集不应该等于完整控件树存储**

这是一个容易产生误区的地方。

假设用户打开一篇新闻文章，页面有 100 个控件。

你可能只需要：

- 页面属于新闻阅读页。
- 文章标题。
- 新闻来源。
- 当前页面的主题。
- 用户是否进行了收藏或分享。

而不需要保存：

- 所有按钮。
- 广告控件。
- 底部导航。
- 无关图片描述。
- 所有布局节点。

因此我建议采用：

**控件树快速解析 → 页面模板匹配 → 关键字段提取 → 只保存必要字段。**

如果模板匹配失败，才考虑进一步增强理解。

### **3. 深度采集：利用小艺页面理解能力**

你提到小艺已有页面理解功能，这确实是一个值得优先利用的方向。

不过这里需要区分两种能力：

**A. 页面结构获取**

基础能力

获取页面中可访问的控件、文本、层级、交互属性等。

解决：页面上有什么？

**B. 页面语义理解**

增强能力

结合视觉布局、控件关系、上下文，理解页面的业务含义。

解决：这些内容代表什么业务？用户在完成什么操作？

例如用户进入订单详情页面：

[12306改签火车票步骤，改签火车票的手续费_车主手册](https://images.openai.com/static-rsc-4/qRHwUzb_0RKRCMFuCO66ekn1lq9gUjjrQasJ1NwkWfEonlnqFxLI6LqsS-s0ESL3z3HJotsBKCmGPjkaVhz7uL6qXVgyLwl518rh7zB6agHqKx5AMNqGEqteMPXAmtF7r1tJXW0Yd9RICuIcxFpqPHUR_rbe-TX93v1A4_syORU?purpose=inline)

[icauto.com.cn](https://www.icauto.com.cn/chuxing/77/775177.html?utm_source=chatgpt.com)

控件树可能获取到：

```
Text: 北京南
Text: 上海虹桥
Text: G101
Text: 08:00
Text: 12:30
Text: 12月3日
Text: 已支付
```

但页面理解需要进一步判断：

- 北京南是出发站。
- 上海虹桥是到达站。
- G101 是车次。
- 08:00 是出发时间。
- 12:30 是到达时间。
- 已支付意味着这是一笔已经完成支付的订单，而不是搜索结果。

这就是页面结构与业务语义之间的差别。

### **4. 小艺页面理解能不能直接被你的系统调用？**

这里我需要特别提醒一个工程边界：

**小艺能够理解屏幕内容，不等于它向第三方系统服务开放了一个可以在后台任意调用的通用页面理解 API。**

华为目前公开的小艺能力包括基于屏幕内容和用户意图进行理解，以及通过小艺开放平台接入 Agent、Skill 和意图框架。但这些公开能力不能直接推导出你的系统服务可以在用户无感知的情况下，持续调用小艺内部的页面理解引擎。

我建议你将其作为一个可插拔的页面理解 Provider：

```

    |

    |
```

### **5. OpenHarmony 工程上需要区分两条实现路线**

这点尤其重要。

**路线 A：你开发的是系统级 AI 桌面服务。**

如果具备系统签名、相应 APL 权限和系统接口开放条件，可以考虑由系统服务统一获取页面信息，再交给采集引擎处理。

**路线 B：你开发的是普通第三方应用。**

不能假设它可以任意读取其他应用的页面控件树。

HarmonyOS 的应用沙箱和访问控制明确限制跨应用数据访问。Accessibility Kit 有无障碍服务相关能力，但是否能以你的部署形态使用、能读取哪些窗口信息，需要按目标 API 版本和权限逐项确认。

# **四、经过采集后，是否形成结构化数据，再进行语义理解推理？**

完全正确。

但我建议你在这里增加一个中间层：

**原始观察数据 → 页面业务数据 → 用户行为事件 → 场景上下文 → 意图推理。**

不要从控件树直接跳到 LLM。

这几个层次需要严格区分。

## **1. 第一层：原始观察数据（Raw Observation）**

保留必要的原始证据。

例如：

```
{
  "observation_id": "obs_001",
  "timestamp": "2026-11-26T09:01:25",
  "bundle_name": "com.example.railway",
  "window_id": "window_01",
  "page_fingerprint": "hash_001",
  "source": "accessibility_tree",
  "observed_nodes": [
    {
      "node_id": "node_01",
      "text": "北京南",
      "role": "Text"
    },
    {
      "node_id": "node_02",
      "text": "上海虹桥",
      "role": "Text"
    },
    {
      "node_id": "node_03",
      "text": "2026-12-03",
      "role": "DatePicker"
    }
  ]
}
```

原始数据主要用于追溯和重新解析。

不需要把所有控件树长期保存，可以采用短期缓存、字段抽取后删除原始内容的策略。

## **2. 第二层：页面业务数据（Page Semantic Data）**

把原始控件映射成业务字段。

例如：

```
{
  "page_type": "TRAIN_SEARCH",
  "business_object": "TRAIN_QUERY",
  "fields": {
    "departure_station": "北京南",
    "arrival_station": "上海虹桥",
    "departure_date": "2026-12-03"
  },
  "field_provenance": {
    "departure_station": {
      "source_node": "node_01",
      "extract_method": "control_mapping",
      "confidence": 0.99
    }
  }
}
```

这里的 `field_provenance` 很重要。

它可以回答：系统为什么认为北京南是出发站？

是根据控件标签、页面模板，还是模型推理得到的？

不同来源的可信程度不一样。

## **3. 第三层：用户行为事件（User Action Event）**

这里必须保留用户实际做了什么，而不是仅仅保留页面内容。

例如：

```
{
  "event_id": "evt_001",
  "timestamp": "2026-11-26T09:01:25",
  "bundle_name": "com.example.railway",
  "page_type": "TRAIN_SEARCH",
  "action_type": "SEARCH_SUBMIT",
  "business_object": {
    "type": "TRAIN_QUERY",
    "departure_station": "北京南",
    "arrival_station": "上海虹桥",
    "departure_date": "2026-12-03"
  },
  "event_status": "OBSERVED"
}
```

这里的 `OBSERVED` 意味着系统观察到用户进行了相关操作，但还不能确认服务器查询成功。

如果后续观察到搜索结果页面，才可以产生一个搜索结果事件。

这样可以避免把用户填写了搜索条件误认为已经完成查询。

## **4. 第四层：场景上下文（Scenario Context）**

将多个真实事件关联起来。

例如：

```
{
  "scenario_id": "scene_001",
  "scenario_type": "RAIL_TRAVEL_PLANNING",
  "time_range": {
    "start": "2026-11-26T09:00:00",
    "end": "2026-11-26T09:20:00"
  },
  "related_events": [
    "evt_001",
    "evt_002",
    "evt_003",
    "evt_004"
  ],
  "entities": {
    "departure_stations": ["北京南"],
    "arrival_stations": ["上海虹桥", "南京南"],
    "travel_dates": ["2026-12-03"]
  },
  "scenario_status": "ACTIVE"
}
```

注意这里不应该把北京到上海、北京到南京合并成一个出行目的地。

它们是两条不同的候选出行方案。

场景层负责把事件关联起来，不负责提前把不同业务对象强行归并。

# **五、用户真实操作数据应该采集到什么程度？——以铁路购票为例**

这是你第六个问题，也是我认为之前方案最需要完善的地方。

我建议你不要把铁路购票抽象成一个 `TRAIN_TRAVEL` 事件，而是建立完整的业务对象模型。

至少需要区分：

1. 搜索行为。
2. 搜索条件。
3. 搜索结果。
4. 车次详情。
5. 订单行为。
6. 订单状态。
7. 退改签行为。

这几类信息有完全不同的业务含义。

## **1. 搜索行为：保留每一次查询的完整条件**

假设用户进行了以下操作：

| 时间    | 操作    | 查询条件             |
| ----- | ----- | ---------------- |
| 09:00 | 搜索车票  | 北京南 → 上海虹桥，12月2日 |
| 09:03 | 修改日期  | 北京南 → 上海虹桥，12月3日 |
| 09:05 | 修改目的地 | 北京南 → 南京南，12月3日  |
| 09:08 | 再次查询  | 北京南 → 上海虹桥，12月3日 |
| 09:10 | 查看车次  | G101             |

这时必须保存每一次查询，而不能只保存最后一次查询。

建议的数据结构：

```
{
  "query_id": "query_001",
  "query_type": "TRAIN_TICKET_SEARCH",
  "query_time": "2026-11-26T09:00:00",
  "query_conditions": {
    "departure_station": {
      "name": "北京南",
      "code": "VNP"
    },
    "arrival_station": {
      "name": "上海虹桥",
      "code": "AOH"
    },
    "departure_date": "2026-12-02",
    "departure_time_range": null,
    "train_type": null,
    "seat_type": null
  },
  "result_status": "RESULT_PAGE_OBSERVED"
}
```

后续每次修改搜索条件，都应该生成新的查询记录。

这样可以识别用户的行为变化：

- 用户在比较不同目的地。
- 用户在调整出发时间。
- 用户反复关注某一条线路。
- 用户可能已经确定出行日期。
- 用户可能正在筛选合适车次。

特别注意：如果用户只是修改了搜索框，没有真正提交查询，应该记录为 `QUERY_CONDITION_EDIT`，不能算作一次已提交查询。

## **2. 搜索结果：不仅采集搜索条件，还要采集用户关注的结果**

例如用户查询北京到上海，系统展示：

| 车次   | 出发时间  | 到达时间  | 历时     |
| ---- | ----- | ----- | ------ |
| G101 | 08:00 | 12:30 | 4小时30分 |
| G103 | 09:00 | 13:25 | 4小时25分 |
| G105 | 10:00 | 14:40 | 4小时40分 |

用户打开 G101 详情页面。

系统至少要保留：

```
{
  "result_id": "result_001",
  "query_id": "query_004",
  "result_type": "TRAIN",
  "train_number": "G101",
  "departure_station": "北京南",
  "arrival_station": "上海虹桥",
  "departure_time": "08:00",
  "arrival_time": "12:30",
  "travel_date": "2026-12-03",
  "user_action": "DETAIL_VIEW"
}
```

这样才能区分：

- 用户只是搜索过北京到上海。
- 用户查看过 G101。
- 用户重点关注了 G101。
- 用户最终购买了 G101。

这些信息不能混为一谈。

另外，搜索结果可能动态变化，不必把全部车次列表永久保存。建议只保存用户实际点击、关注、选择的结果，以及必要的结果摘要。

## **3. 订单行为：必须和搜索行为严格区分**

假设用户进入订单详情页，看到：

- 订单号。
- 北京南 → 上海虹桥。
- G101。
- 12月3日。
- 08:00 出发。
- 12:30 到达。
- 已支付。

这时，系统已经掌握了比搜索行为更高确定性的事实。

建议建立独立的订单数据对象：

```
{
  "order_id": "order_001",
  "business_type": "TRAIN_ORDER",
  "order_status": "PAID",
  "travel": {
    "departure_station": "北京南",
    "arrival_station": "上海虹桥",
    "travel_date": "2026-12-03",
    "train_number": "G101",
    "departure_time": "08:00",
    "arrival_time": "12:30"
  },
  "observation": {
    "source": "ORDER_DETAIL_PAGE",
    "observed_at": "2026-11-26T09:30:00",
    "confidence": 0.99
  }
}
```

注意：

这里的 `PAID` 只有在页面明确展示已支付，或者得到可信的订单状态数据时才能赋值。

如果只是打开订单详情页，但页面状态无法读取，应该标记为 `UNKNOWN`，不能根据用户进入订单页就推断已经付款。

订单号、乘客姓名、身份证号、支付信息等不应默认进入通用意图模型。对于识别出行意图而言，大部分都不是必要字段。

## **4. 用户反复查询不同路线，如何理解？**

这是一个非常典型的跨事件推理问题。

假设用户：

```
09:00 北京 → 上海，12月2日
09:03 北京 → 上海，12月3日
09:05 北京 → 南京，12月3日
09:08 北京 → 上海，12月3日
09:10 查看G101
09:30 查看已支付订单
```

系统不能简单得出：

用户计划去上海和南京。

应该保留多种假设：

**场景候选分析**

**候选 A：北京 → 上海**

强证据

- 多次重复查询
- 修改日期后再次查询
- 查看具体车次
- 后续观察到已支付订单

**候选 B：北京 → 南京**

待确认

- 查询过一次
- 没有进一步查看车次
- 没有发现对应订单

如果已支付订单明确对应北京到上海，那么上海这条出行计划的确定性显著提高。

南京则应该保留为历史查询行为，不能自动认定用户还要去南京。

这就是为什么你的系统需要保留完整的业务对象、事件时间和事件之间的关联关系。

## **5. 我建议建立一套统一的业务对象类型**

不要让所有信息都以自由文本的方式存在。

建议第一阶段定义：

| 业务领域 | 业务对象                                      |
| ---- | ----------------------------------------- |
| 出行   | TravelQuery、TravelOption、TravelOrder      |
| 酒店   | HotelSearch、HotelOption、HotelOrder        |
| 会议   | Meeting、MeetingInvitation、MeetingLocation |
| 购物   | ProductSearch、ProductView、PurchaseOrder   |
| 餐饮   | RestaurantSearch、RestaurantOrder          |
| 通信   | MessageEvent、EmailEvent、ContactEntity     |
| 日程   | CalendarEvent、ReminderEvent               |

每个业务对象都有自己的字段定义和状态。

这样后续无论是用规则、LightGBM 还是 LLM，都能处理统一的数据协议。

# **六、结构化数据形成后，如何进行语义理解和推理？**

你理解的流程是对的，但我建议采用两阶段推理。

**第一阶段：事实抽取与事实关联。**

**第二阶段：意图假设与任务推理。**

这两个阶段不能混淆。

## **1. 第一阶段：把事实整理出来**

例如：

```
事实 F1：
11月26日 09:00
查询北京南 → 上海虹桥
出发日期12月3日

事实 F2：
11月26日 09:05
查询北京南 → 南京南
出发日期12月3日

事实 F3：
11月26日 09:10
查看G101
北京南 → 上海虹桥
12月3日 08:00

事实 F4：
11月26日 09:30
订单详情显示已支付
北京南 → 上海虹桥
G101
12月3日
```

这里的事实应该是结构化记录，不应该让模型重新猜测已经明确的字段。

## **2. 第二阶段：推理用户可能在做什么**

此时再把上述事实交给语义推理模型。

让模型回答：

- 可能的用户意图是什么？
- 哪些信息已经确认？
- 哪些信息存在冲突？
- 哪些内容只是推测？
- 哪些关键内容还不明确？
- 是否形成一个独立任务？
- 下一步最值得提供什么服务？

例如：

**模型推理结果**

已发现出行任务

**任务：北京至上海出行**

**已确认事实**

- 出发地：北京南
- 目的地：上海虹桥
- 出发日期：12月3日
- 车次：G101
- 出发时间：08:00
- 订单状态：已支付

**待确认内容**

- 是否有会议安排？
- 是否已经预订酒店？
- 是否需要准备会议材料？

**历史关联**

\- 曾查询北京至南京，但尚无证据证明这是已确定行程。

**推荐动作**

- 生成出行信息卡片。
- 整理已确认车票信息。
- 检查是否存在相关日程。
- 暂不推送酒店预订提醒。

我特别建议在推理输出中明确区分三种信息：

| 信息类别                | 含义       | 处理原则      |
| ------------------- | -------- | --------- |
| Confirmed Facts     | 有直接证据的事实 | 可以展示      |
| Inferred Facts      | 根据多个事实推断 | 标记为推测     |
| Missing Information | 当前无法确定   | 可以继续观察或询问 |

另外，还需要增加 `Conflicting Facts`，用于处理时间、地点、订单状态等相互矛盾的证据。

例如，用户先查询12月2日，后查询12月3日，不能把两个日期同时认定为最终出行日期。

# **七、是否推送？意图明确性是否需要决策模型？**

是的，我认为这里应该有独立的决策模型。

但是要把两个决策分开：

1. 是否创建任务？
2. 是否向用户推送？

这两个问题不能用同一个阈值解决。

例如：

用户已经明确购买了车票，任务可以确认创建。

但这不代表系统必须立即推送通知。

反过来，用户可能还没有明确是否出差，但系统发现一个非常关键的日程冲突，这时也可能值得提醒用户。

## **1. 意图明确性模型**

我建议先使用规则和轻量模型结合，不要一开始就训练复杂的深度学习模型。

决策特征包括：

| 特征    | 说明              |
| ----- | --------------- |
| 证据数量  | 有多少条相关事件        |
| 证据可信度 | 来自搜索页还是订单详情     |
| 事件关联度 | 不同应用的数据是否指向同一任务 |
| 时间一致性 | 日期是否一致          |
| 实体一致性 | 地点、人物、业务对象是否一致  |
| 行为连续性 | 是否持续围绕同一任务操作    |
| 任务确定性 | 是否有订单、邀请、日程等强证据 |
| 冲突程度  | 是否存在互相矛盾的信息     |

我建议使用一个轻量级的任务确认模型：

```
输入：
  事件特征
  业务对象
  证据可信度
  时间关系
  实体关联
  冲突信息

输出：
  intent_confidence
  task_confidence
  task_stage
  need_more_collection
```

这里不一定需要一个独立的神经网络。

第一版完全可以用规则评分 + LightGBM。

## **2. 推送模型应该考虑什么？**

我建议把推送看作一个独立的效用决策。

可以设计一个初步评分：

\\[ S\_{push}=0.30C+0.25V+0.20T+0.15A-0.10I \\]

其中：

- \\(C\\)：意图和事实的可信度。
- \\(V\\)：推荐内容对用户的价值。
- \\(T\\)：当前推送时机的适合程度。
- \\(A\\)：与用户偏好的匹配度。
- \\(I\\)：对用户的打扰成本。

各项先归一化为 0～1。

这个公式只是 V1 的初始策略示例，权重应通过用户反馈和离线评估调整，不能把它当成已经验证的最优模型。

### **3. 建立推送等级**

| 推送等级 | 条件         | 处理方式         |
| ---- | ---------- | ------------ |
| P0   | 意图不明确      | 不推送，继续观察     |
| P1   | 意图可能成立     | 更新 AI 桌面内部任务 |
| P2   | 任务明确、有实际价值 | 生成内容卡片       |
| P3   | 重要且时机合适    | 主动通知用户       |

例如：

- 仅搜索北京到上海：P0/P1。
- 多次搜索并查看车次：P1。
- 已购买车票：可以确认出行任务，P2。
- 车票即将出发，且发现用户日历中有冲突：可能达到 P3。

当然，是否允许访问日历、是否允许主动通知，都要受用户授权和系统通知权限控制。

**我的建议是：任务创建的门槛可以相对低一些，但主动通知的门槛必须高。**

这样系统能够持续积累用户上下文，又不会因为每次发现潜在意图就打扰用户。

# **八、把以上六个问题整合成最终采集架构**

我建议最终不要采用简单的「轻量采集模型 + 深度采集模型」两级结构，而是采用：

**应用识别 + 页面识别 + 采集策略引擎 + 页面解析引擎 + 事件关联引擎 + 意图推理引擎 + 推送决策引擎。**

其中，前面几个模块尽量使用规则和确定性算法，真正复杂的语义推理才使用 LLM。

## **1. 完整数据流**

## **AI 桌面采集与意图理解架构**

**① 应用感知**

包名、应用分类、前后台状态、应用切换

规则匹配：发现候选场景

**② 页面感知**

页面路由、页面指纹、控件树、页面类型

规则 + 页面模板：识别业务页面

**③ 采集策略决策引擎**

**L1 轻量**

页面、路由、操作类型

**L2 字段提取**

业务字段、搜索条件、订单信息

**L3 深度理解**

页面语义、跨页面关系、复杂上下文

规则优先，轻量决策模型辅助，按需启动页面理解

**④ 结构化数据层**

Raw Observation → Page Semantic → User Action Event → Business Object

**⑤ 事件关联与用户上下文**

时间关联、实体关联、跨应用关联、历史行为关联

**⑥ 意图理解与任务推理**

- 轻量决策模型：意图概率和任务确认
- LLM：复杂语义理解、关键内容和待确认内容
- 任务状态机：创建、更新、完成、取消

**⑦ 主动推荐决策**

价值评估、时机判断、打扰成本、用户偏好

**AI 桌面内容卡片 / 主动通知**

## **2. 我建议你第一版先实现的核心算法**

不要急着做完整的多模型体系。先实现三个相对独立的决策点。

| 决策点      | 推荐实现              | 是否需要训练       |
| -------- | ----------------- | ------------ |
| 是否进入增强采集 | 应用白名单 + 页面类型规则    | 不需要          |
| 是否进行深度理解 | 页面价值规则 + LightGBM | 初期不需要，后期需要   |
| 是否创建任务   | 证据规则 + LightGBM   | 有数据后训练       |
| 是否推送     | 任务置信度 + 价值评分 + 规则 | 初期不需要        |
| 复杂语义推理   | 小型端侧 LLM          | 优先预训练模型，后续微调 |

尤其是第三个决策点：是否创建任务。

它不应该只看模型给出的一个置信度，而应该同时看：

- 是否有真实业务对象。
- 是否有关键事件。
- 是否存在强证据。
- 是否存在相互冲突的信息。
- 是否与已有任务重复。

## **九、我认为你现在最应该明确的一个工程边界**

你目前已经把业务逻辑想得比较清楚了，但还需要确定一个关键问题：

**系统究竟能拿到什么数据，决定了你的模型架构，而不是模型架构决定系统能采集什么数据。**

建议先把数据源划分成三种：

| 数据源    | 能获得的信息         | 重要性  |
| ------ | -------------- | ---- |
| 系统事件   | 应用切换、前后台、设备状态  | 基础   |
| 页面感知   | 控件树、页面文本、页面结构  | 核心   |
| 应用业务数据 | 搜索参数、订单状态、交易结果 | 最高质量 |

对于第三方应用，最理想的方式是应用主动提供标准化业务事件或业务数据接口，而不是依赖屏幕解析猜测所有内容。

对于无法合作的应用，再通过页面控件树和页面理解能力尽可能获取信息。

同时，必须建立权限白名单、用户可见的采集开关、敏感字段过滤、数据保留期限和删除机制。尤其是订单、通信、金融等信息，不能因为页面可见就默认允许系统长期采集。HarmonyOS 的访问控制和用户授权机制需要作为系统设计的前置约束。

## **十、我的最终判断**

你现在思考的方向，实际上已经从「端侧模型如何识别用户意图」深入到了一个更重要的问题：

**如何让手机系统获得足够丰富、准确、连续的用户行为上下文，再让模型从这些真实数据中理解用户。**

我认为应该明确以下几个原则：

1. **包名是场景初筛依据，不是场景结论。**
2. **页面路由和页面业务类型决定采集策略。**
3. **控件树优先，页面理解按需触发。**
4. **轻量采集和深度采集的区别是处理深度，而不是简单的数据多少。**
5. **原始观察、业务字段、用户事件必须分层存储。**
6. **搜索记录、浏览记录、订单记录必须区分。**
7. **意图推理必须有证据链，区分事实和推测。**
8. **任务创建和主动推送是两个独立决策。**

我尤其建议你不要过早把 LLM 引入页面采集流程。页面识别、字段提取、业务对象构建，尽可能使用确定性方法完成。这样后续模型训练会更容易，推理成本也更低。

**下一步最值得做的是以铁路购票为样板，把这套架构落实成真正可以开发的工程设计。** 包括页面类型字典、页面采集策略表、控件树解析规则、原始事件数据结构、业务对象 Schema、三个决策器的输入输出协议，以及 HarmonyOS System 模块之间的接口。
