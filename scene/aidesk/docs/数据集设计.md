# **6 小时端侧用户意图推理数据集设计方案**

我建议把这套数据集定义为：

**6H-CrossApp-Intent：面向端侧模型的 6 小时跨应用用户行为意图推理数据集。**

它不是普通的 App 行为分类数据集，而是让模型学习：在一个用户连续 6 小时的行为片段中，面对多个 App、多个业务领域、多个潜在目的和大量无关行为，识别出用户正在形成或推进的意图，并把支持该意图的事件关联起来。

先沿用前面确定的实验约束：

**基础样本规格**

# **6h**

固定行为窗口

# **30**

每条样本事件数

# **15**

无关事件数

# **50%**

无关行为占比

**剩余 15 条相关事件**可以包含直接证据、关联兴趣、反向证据和状态变化。它们不要求全部支持同一个意图。

这里有一个重要定义：**无关行为是相对于当前样本中的全部目标意图而言的无关行为。** 如果一条行为与意图 A 有关、与意图 B 无关，它不能被标成全局无关，而应该记录它与 A 的关联关系。

# **一、整体数据集结构：场景类别 × 推理难度**

我不建议只按照旅游、购物、工作等业务类别生成数据。因为模型最终要解决的核心问题是证据推理，而不是领域分类。

所以建议采用两条维度：

- **场景类别**：用户可能正在做什么。
- **推理难度**：模型需要解决什么样的证据关联问题。

例如，“出行”是场景类别，“机票酒店已确定但目的未知”是推理难度。

## **1. 场景类别设计**

第一版建议覆盖 12 个主要类别。

| 编号  | 场景类别    | 典型意图           | 关键证据              |
| --- | ------- | -------------- | ----------------- |
| C01 | 旅游与出行   | 旅游、商务出差、探亲     | 机票、酒店、地图、日历、会议    |
| C02 | 工作与商务   | 客户会议、项目推进、商务拜访 | 邮件、会议、文档、联系人、日历   |
| C03 | 电商与购物   | 买手机、买家电、购买礼物   | 搜索、比价、商品详情、购物车、支付 |
| C04 | 餐饮与社交   | 聚餐、约会、朋友聚会     | 聊天、餐厅搜索、订座、地图     |
| C05 | 健康与生活服务 | 预约体检、看诊、购买日常用品 | 预约、订单、日历、位置       |
| C06 | 学习与考试   | 备考、报名课程、学习计划   | 课程搜索、报名、支付、学习 App |
| C07 | 娱乐与文体活动 | 演唱会、电影、体育赛事    | 票务、场馆、日历、攻略       |
| C08 | 家庭与个人事务 | 搬家、装修、家庭聚会     | 聊天、家居订单、物业、日历     |
| C09 | 金融与行政事务 | 办理业务、缴费、证件办理   | 银行、政务、预约、材料准备     |
| C10 | 运动与健身   | 健身计划、跑步活动、体育训练 | 运动 App、课程、装备、场馆   |
| C11 | 交通与本地活动 | 周末自驾、租车、周边游    | 租车、地图、停车、天气       |
| C12 | 多意图并行   | 出差同时购物、聚餐同时看演出 | 多个相互独立的证据簇        |

这里的健康场景建议只标注用户明确发生的预约、检查、购药等行为，不要让模型根据零散行为推断疾病或健康状况。

## **2. 场景内部还要细分任务**

例如 C01 出行不能只做“旅游”。

**C01：旅游与出行**

1. **目的地明确、目的未知**

   已购买机票和酒店，但没有商务或旅游目的证据。
2. **旅游目的明确**

   机票、酒店、景点攻略、游玩计划等证据相互印证。
3. **商务出差明确**

   机票、酒店、客户会议、工作邮件、日历会议等证据。
4. **探亲或访友**

   交通安排与亲友沟通、家庭活动安排形成关联。
5. **仅有出行兴趣**

   浏览攻略、搜索目的地，没有实际预订。
6. **计划取消或改变**

   取消机票、退款、改期、切换目的地。

其他类别也应该采用类似方式，尽量同时包含“计划已确定、计划不确定、仅有兴趣、计划变更”几种情况。

建议不要平均分配 12 个类别。因为旅游、工作、购物等场景的行为组合复杂度不同，而且多意图并行需要专门训练。

我建议如下：

| 类别          | 样本数        | 占比       |
| ----------- | ---------- | -------- |
| C01 旅游与出行   | 1,500      | 15%      |
| C02 工作与商务   | 1,200      | 12%      |
| C03 电商与购物   | 1,200      | 12%      |
| C04 餐饮与社交   | 800        | 8%       |
| C05 健康与生活服务 | 600        | 6%       |
| C06 学习与考试   | 700        | 7%       |
| C07 娱乐与文体活动 | 800        | 8%       |
| C08 家庭与个人事务 | 600        | 6%       |
| C09 金融与行政事务 | 500        | 5%       |
| C10 运动与健身   | 500        | 5%       |
| C11 交通与本地活动 | 600        | 6%       |
| C12 多意图并行   | 1,000      | 10%      |
| **合计**      | **10,000** | **100%** |

这个分布是初始实验配比，不代表真实用户行为的发生频率。

特别是 C12，建议独立设计，而不是把其他类别的样本简单拼接起来。多意图样本要有真正独立的事件簇，并且要测试模型能不能把它们分开。

## **1. 每个场景内部的推理难度分布**

每个场景再按照以下比例生成：

| 难度            | 占比  | 例子           |
| ------------- | --- | ------------ |
| D1 单一强证据      | 15% | 已支付订单        |
| D2 多 App 证据融合 | 25% | 机票 + 酒店 + 日历 |
| D3 弱证据和不确定意图  | 20% | 搜索、浏览、收藏     |
| D4 噪声和干扰      | 15% | 大量无关行为穿插     |
| D5 多意图或事件交叉   | 15% | 出差 + 购物      |
| D6 冲突和状态变化    | 10% | 退款、取消、改期     |

这意味着，即使是“旅游”类别，也要包含用户只有攻略浏览、机票酒店齐全但目的未知、出差与旅游兴趣混合等不同情况。

# **三、6 小时行为序列应该怎么生成？**

这是整个数据集设计里非常重要的一部分。

我建议每条样本都采用 30 条事件，但不能简单生成 15 条相关行为，再随机塞入 15 条无关行为。这样会形成很明显的人工数据特征。

## **1. 30 条事件的组成**

**推荐的事件组成**

**直接支持证据**

# **8～10 条**

**关联兴趣或弱证据**

# **3～5 条**

**反向证据或状态变化**

# **0～2 条**

**全局无关行为**

# **15 条**

以上是典型样本的建议结构。反向证据不是每条样本都必须有；无反向证据时，相关事件总数仍需补足 15 条。

例如一个“购买手机”的样本：

- 8 条直接证据：搜索手机、查看详情、比较配置、加入购物车、支付等；
- 7 条弱证据或关联行为：查看手机测评、浏览配件、搜索保护壳；
- 15 条无关行为：看新闻、聊天、买食品、听音乐等。

但如果用户只是浏览手机测评，没有购买行为，就不能硬凑 8 条直接证据。应该让这条样本成为“弱证据、未知购买计划”样本。

**标签应该由事件真实含义决定，不能为了满足配比而篡改事实。** 15 条相关事件是数据构造目标，不应凌驾于标签真实性。如果某个自然场景确实难以提供 15 条相关事件，就应更换场景组合，或将其归入专门的低相关密度测试组，而不是人为提高关联度。

## **2. 事件时间分布**

6 小时内的 30 条事件不要等间隔生成。

建议采用混合分布：

| 时间段      | 事件数量建议 | 典型行为          |
| -------- | ------ | ------------- |
| 第 0～1 小时 | 4～7 条  | 初始搜索、沟通、查看    |
| 第 1～2 小时 | 3～6 条  | 比较、浏览、确认      |
| 第 2～4 小时 | 8～12 条 | 关键操作、跨 App 行为 |
| 第 4～6 小时 | 5～9 条  | 支付、创建日历、后续准备  |

这不是固定模板。要让部分样本在窗口开始时就有强证据，部分样本则在最后一小时才出现决定性证据。

还要特别构造以下情况：

- 关键行为之间间隔 5～10 分钟；
- 关键行为之间间隔 1～2 小时；
- 相关行为中间夹杂 5～10 条无关行为；
- 最关键的确认行为发生在窗口末尾；
- 6 小时内只有一部分意图证据，其他信息需要保留为未知。

这样才能测出模型对时间间隔和事件顺序的理解能力。

# **五、统一输入数据 Schema**

为了让数据可以批量生成、训练和评测，我建议所有场景使用同一个输入结构。不同场景只改变 `events[].content` 和事件组合。

建议分为五部分：

| 字段                  | 用途              |
| ------------------- | --------------- |
| `sample_id`         | 样本唯一标识          |
| `window`            | 固定 6 小时窗口       |
| `history_intents`   | 已有意图状态，可为空      |
| `events`            | 30 条结构化行为       |
| `scenario_metadata` | 仅用于数据管理，不作为模型输入 |

其中，`scenario_metadata` 不应该暴露给模型，否则模型可能直接根据 `scenario_category=travel` 猜答案。

**推荐输入结构：**

```

{
  "sample_id": "C01-000001",
  "task": "cross_app_intent_reasoning",
  "window": {
    "start": "2026-12-01T09:00:00+08:00",
    "end": "2026-12-01T15:00:00+08:00",
    "duration_hours": 6
  },
  "history_intents": [],
  "events": [
    {
      "event_id": "e001",
      "timestamp": "2026-12-01T09:10:00+08:00",
      "app": "travel_app",
      "action": "search_flight",
      "content": {
        "departure": "深圳",
        "destination": "成都",
        "departure_date": "2026-12-18"
      }
    }
  ]
}

```

实际每条样本必须有 30 个事件。这里展示的是结构示意，不是完整样本。

## **1. App 名称和动作类型要不要固定？**

建议固定一套标准动作词表，但不要把 App 限制得太死。

例如：

| 标准动作              | 含义     |
| ----------------- | ------ |
| `search`          | 搜索     |
| `view_detail`     | 查看详情   |
| `browse_content`  | 浏览内容   |
| `collect`         | 收藏     |
| `compare`         | 比较     |
| `create_order`    | 创建订单   |
| `pay`             | 支付     |
| `cancel`          | 取消     |
| `refund`          | 退款     |
| `create_event`    | 创建日历事件 |
| `update_event`    | 修改日历事件 |
| `send_message`    | 发送消息   |
| `receive_message` | 接收消息   |
| `search_route`    | 搜索路线   |
| `book_service`    | 预约服务   |

动作名称统一后，模型学到的是业务语义，而不是某个 App 的特定文案。

同时建议保留 `app` 字段，让模型学习跨应用的证据关联，但在测试集里要有没在训练集中出现过的 App 名称或 App 组合，检查模型是否过度依赖品牌名称。

# **六、统一输出 Schema：必须让模型回答哪些问题？**

我建议不要只输出 `intent_name` 和 `intent_summary`。对于你的任务，最关键的是让模型提供可验证的结构化证据。

每条意图至少应包含：

1. 意图是什么；
2. 意图类别是什么；
3. 具体目的是否明确；
4. 当前状态是什么；
5. 哪些事件直接支持；
6. 哪些事件只是相关兴趣；
7. 哪些事实已经确认；
8. 哪些内容只是推断；
9. 哪些内容仍然未知；
10. 是否存在冲突。

**推荐输出 Schema：**

```

{
  "sample_id": "C01-000001",
  "intents": [
    {
      "intent_id": "i001",
      "intent_name": "成都出行",
      "category": "travel",
      "purpose": "unknown",
      "status": "planned",
      "confidence_level": "high",
      "supporting_event_ids": [],
      "related_interest_event_ids": [],
      "contradicting_event_ids": [],
      "confirmed_facts": [
        {
          "fact": "用户已购买深圳到成都的机票",
          "source_event_ids": ["e005"]
        }
      ],
      "inferred_facts": [
        {
          "fact": "用户计划前往成都",
          "source_event_ids": ["e005", "e009"]
        }
      ],
      "unknown_information": [
        "此次出行的具体目的",
        "是否有同行人"
      ],
      "conflicts": []
    }
  ],
  "event_labels": [
    {
      "event_id": "e001",
      "relation": "supporting",
      "intent_ids": ["i001"]
    }
  ],
  "unrelated_event_ids": [],
  "global_observations": {
    "intent_count": 1,
    "unrelated_event_count": 15
  }
}

```

其中 `purpose` 不应该只支持旅游、商务。建议采用统一的分类体系：

```
{
  "travel": [
    "tourism",
    "business",
    "visiting",
    "commuting",
    "other",
    "unknown"
  ],
  "shopping": [
    "personal_use",
    "gift",
    "work_related",
    "household",
    "unknown"
  ],
  "work": [
    "meeting",
    "project",
    "interview",
    "business_development",
    "unknown"
  ]
}
```

不同类别可以有不同的目的枚举，但都必须保留 `unknown`。

另外，`confidence_level` 是模型对整体意图判断的等级，不等于某条事实的可信度。建议先使用 `low / medium / high`，不要一开始就要求模型生成看似精确的 0.87 之类概率。

# **七、样本生成策略：不能只靠大模型自由生成**

建议采用“场景模板 + 事件库 + 证据组合 + 噪声注入 + 人工审核”的方式。

**数据生成流水线**

**① 场景模板库**

12 个类别、多个子场景

**② 证据事件库**

搜索、浏览、沟通、订单、支付、日历等

**③ 组合与时间编排**

6 小时内形成 30 条事件，相关 15 条、无关 15 条

**④ 自动生成标准标签**

意图、证据引用、事实、推断、未知

**⑤ 规则校验 + 人工审核**

数量、时间、标签一致性、推理正确性

**⑥ 输出 JSONL 训练集与测试集**

## **1. 事件库需要分层**

每个场景都要建立三种事件：

- 强证据事件：支付、确认、预约、已创建日历、明确承诺。
- 弱证据事件：搜索、浏览、收藏、比较、查看详情。
- 干扰事件：与所有目标意图无关的聊天、新闻、视频、日常消费等。

另外建立一套冲突事件：

- 取消订单；
- 退款；
- 改变日期；
- 改变目的地；
- 取消会议；
- 拒绝邀约；
- 重新下单。

冲突事件不能简单当成噪声，因为它们可能直接改变意图状态。

## **2. 同一个场景至少生成五种变体**

以“演唱会”为例：

| 版本 | 输入差异      | 目标答案     |
| -- | --------- | -------- |
| A  | 浏览演唱会视频   | 兴趣       |
| B  | 搜索演唱会门票   | 可能有计划    |
| C  | 选座但未支付    | 购票意向     |
| D  | 支付门票并创建日历 | 演唱会计划    |
| E  | 支付后退票     | 原计划取消或变更 |

这类变体是训练模型区分行为阶段的关键。

## **3. 无关事件要有多样性**

建议无关事件库至少包含：

- 日常聊天；
- 新闻阅读；
- 娱乐视频；
- 音乐播放；
- 日常购物；
- 日常支付；
- 工作消息；
- 天气查看；
- 普通地图查询；
- 其他无关搜索。

并且要避免所有无关事件都放在窗口前半段或后半段。它们应该随机穿插在关键事件之间。

# **八、训练集、验证集和测试集怎么划分？**

我建议按以下结构组织 10,000 条样本：

10,000 条样本的初始数据划分建议。

02,0004,0006,0008,000训练集验证集测试集挑战集

其中：

- 训练集：覆盖所有场景和常见证据组合。
- 验证集：与训练集场景类别相同，但行为顺序、实体和事件组合不同。
- 测试集：使用训练中没有出现过的场景模板、目的地和 App 组合。
- 挑战集：专门测试弱证据、多意图、冲突、噪声和未知判断。

**不要简单随机划分。**

建议至少做三种隔离：

1. 场景模板隔离：同一模板的改写版本不能跨训练集和测试集。
2. 实体组合隔离：例如训练集使用东京、成都，测试集可以使用其他目的地。
3. 用户行为模式隔离：同一模拟用户的行为习惯不要同时出现在训练和测试中。

测试集还可以额外设计一个“跨 App 组合留出”实验：训练中出现携程 + 美团，测试中使用航旅纵横 + 其他酒店平台。这样才能知道模型是否学会了业务关联，而不是记住 App 组合。

# **九、评测体系：重点评估模型是否真的会推理**

我建议不要用一个综合准确率评价模型。应该至少拆成六个评测维度。

| 评测维度  | 指标                             | 主要问题             |
| ----- | ------------------------------ | ---------------- |
| 意图识别  | Intent Precision / Recall / F1 | 是否找到正确意图         |
| 事件关联  | Event-to-Intent F1             | 是否关联正确的事件        |
| 证据等级  | Relation Macro-F1              | 能否区分强证据、兴趣、冲突、无关 |
| 目的判断  | Purpose Accuracy / Macro-F1    | 能否正确识别旅游、商务、未知等  |
| 事实可靠性 | Fact Precision                 | 是否编造或错误表述事实      |
| 不确定性  | Unknown Accuracy               | 是否知道什么时候不能下结论    |

## **1. 事件关联评测**

这应该是整个数据集最重要的指标。

例如测试样本中，模型识别出“成都出行”，但把 30 条事件全部关联到该意图，那么：

- 意图名称可能正确；
- 意图识别 F1 可能较高；
- 事件关联 Precision 却会很低。

这说明模型只识别了主题，没有真正理解事件之间的关系。

因此必须分别计算：

- `supporting` 的 Precision、Recall、F1；
- `related_interest` 的 Precision、Recall、F1；
- `contradicting` 的 Precision、Recall、F1；
- `unrelated` 的 Precision、Recall、F1。

建议使用 Macro-F1，避免因为无关事件较多而掩盖弱证据识别能力差的问题。

## **2. 意图目的评测**

特别设计一组目的识别对照实验：

| 事件组合                  | 正确答案        |
| --------------------- | ----------- |
| 搜索东京攻略                | 目的地兴趣       |
| 搜索东京机票                | 可能出行        |
| 已购买东京机票 + 酒店          | 东京出行，目的未知   |
| 机票 + 酒店 + 客户会议        | 商务出行        |
| 机票 + 酒店 + 景点计划        | 旅游出行        |
| 机票 + 酒店 + 客户会议 + 景点兴趣 | 商务出行，兼有旅游兴趣 |

这里建议重点计算：

**Purpose Over-inference Rate（目的过度推断率）**

例如，真实标签为 `unknown`，模型却输出 `tourism` 或 `business`，就属于过度推断。

这项指标应该单独报告，而不是隐藏在整体准确率中。

## **3. 多意图评测**

C12 场景建议单独计算：

- 意图数量识别准确率；
- 意图之间的事件分离准确率；
- 多意图事件交叉关联准确率；
- 意图合并错误率；
- 意图拆分错误率。

例如：

用户上午订购手机，下午安排成都出差。模型不能把它们合并成一个“成都购物旅行”。

## **4. 事实和证据评测**

每一个事实都应该能追溯到输入事件。

建议设计三个指标：

- `Fact Grounding Precision`：事实是否有输入依据。
- `Evidence Citation Accuracy`：引用的事件是否真的支持该事实。
- `Unsupported Claim Rate`：模型输出了多少没有证据支持的内容。

对于这类端侧意图模型，我认为 `Unsupported Claim Rate` 尤其重要。

## **5. 建议的首版目标线**

下面是建议作为研发阶段目标的参考线，并非已有模型实测结果：

| 指标                       | 初期目标  |
| ------------------------ | ----- |
| 意图识别 Macro-F1            | ≥ 85% |
| 事件关联 Macro-F1            | ≥ 80% |
| Supporting Event F1      | ≥ 85% |
| Related Interest F1      | ≥ 75% |
| Purpose Accuracy         | ≥ 85% |
| Fact Grounding Precision | ≥ 95% |
| Unknown 识别准确率            | ≥ 90% |

注意：这些目标最好在人工审核的独立测试集上计算。模型输出 JSON 格式正确，只代表结构符合要求，不代表推理正确。

# **十、训练策略：建议分三个阶段，而不是一次性混合训练**

虽然最终数据集要包含 12 个类别，但第一轮不建议将全部复杂样本直接混合训练。

**阶段一：单意图、强证据**

先学会找证据

- 旅游、购物、会议、演唱会等单一场景。
- 多 App 强证据组合。
- 30 条事件中有 15 条无关行为。
- 训练模型输出意图、证据事件和确认事实。

**阶段二：弱证据、歧义和目的判断**

再学会克制

- 只有搜索、浏览、收藏。
- 目的地明确但目的未知。
- 多个候选目的。
- 相关兴趣与已确定计划的区别。
- 取消、退款、冲突行为。

**阶段三：多意图和复杂关联**

最后学习组合推理

- 同一窗口多个独立意图。
- 一个事件关联多个意图。
- 多个 App 之间的证据交叉。
- 一个意图中出现支持与反向证据。

这样做的好处是：先让模型学会证据与意图的基本关系，再学习证据不足时如何保持不确定，最后才处理多意图的复杂推理。

## **十一、数据质量控制：我认为有五个地方必须严格把关**

### **1. 不要让 App 名称直接暴露答案**

如果训练样本里所有携程行为都代表旅游、所有钉钉行为都代表工作，模型可能只学会了 App 分类。

要让相同 App 在不同场景中承担不同角色。

例如：

- 微信可以是商务会议证据；
- 微信可以是家庭聚会证据；
- 微信也可以是无关日常聊天。

### **2. 不要让时间顺序成为固定模板**

不要每条样本都是：

搜索 → 浏览 → 下单 → 支付 → 日历。

应该同时包含：

- 先沟通，后搜索；
- 先购买，后补充日历；
- 先创建日历，后完成支付；
- 先有订单，后出现取消；
- 相关行为和无关行为交错。

### **3. 不要让相关行为总是关键词相同**

例如“东京”可能分别出现在：

- 机票订单；
- 酒店预订；
- 客户会议；
- 新闻内容；
- 朋友聊天；
- 旅游攻略。

模型需要理解事件的业务语义，而不只是统计关键词共现。

### **4. 不要让合成数据的噪声过于简单**

无关行为不能全部是看视频、听音乐。

应该加入一些容易混淆的行为：

- 浏览其他城市的攻略；
- 搜索其他日期的机票；
- 查看其他城市的酒店；
- 与朋友讨论另一个活动；
- 工作聊天中提到某个旅游地点。

这类干扰比纯随机噪声更有训练价值。

### **5. 不要让测试集复用训练集的模板**

即使更换城市名称，如果事件顺序、App 组合和字段内容完全一致，也不能算真正的泛化测试。

建议每个场景建立多套独立模板，并且将部分模板完整留给测试集。

# **十二、最终建议的数据集建设路线**

我建议按照下面的顺序推进：

| 阶段 | 交付物            | 建议规模        |
| -- | -------------- | ----------- |
| P0 | 统一 Schema、标签定义 | 1 套         |
| P1 | 12 个场景的模板库     | 60～100 套模板  |
| P2 | 高质量人工审核样本      | 500～1,000 条 |
| P3 | 第一版 SFT 数据集    | 7,000 条     |
| P4 | 验证集和常规测试集      | 2,500 条     |
| P5 | 挑战测试集          | 500 条       |
| P6 | 端侧模型评测报告       | 1 份         |

这里有个值得强调的点：第一版 10,000 条样本不一定全部都需要人工逐条编写。可以让模型按照固定模板生成事件序列和候选标签，再由规则程序校验数量、时间、ID 和证据引用，最后由人工抽检和重点审核高歧义样本。

但测试集，尤其是挑战集，应该由独立流程构造并经过人工审核，不能直接使用训练数据生成器的默认模板。

## **十三、我建议额外保留三个专项测试集**

除了常规测试集，我认为还应该单独保留：

| 专项测试集  | 规模建议 | 要回答的问题           |
| ------ | ---- | ---------------- |
| 弱证据测试集 | 200  | 模型会不会过度推断？       |
| 多意图测试集 | 200  | 模型能不能识别并行意图？     |
| 强噪声测试集 | 100  | 15 条无关行为能否被正确排除？ |

这三个测试集比单纯扩大常规测试集更有价值。

## **最终数据集规格汇总**

# **6H-CrossApp-Intent v1.0**

建议基线规格

| 项目     | 设计                         |
| ------ | -------------------------- |
| 时间窗口   | 固定 6 小时                    |
| 每条事件数  | 30 条                       |
| 全局无关事件 | 15 条                       |
| 相关事件   | 15 条                       |
| 场景类别   | 12 类                       |
| 总样本规模  | 10,000 条                   |
| 输出     | 结构化 JSON                   |
| 核心能力   | 多 App 证据关联、意图推理、未知判断、多意图识别 |
| 测试重点   | 证据正确性、误推断、噪声排除、跨场景泛化       |

**我最建议优先做好的三个场景：**

1. 旅游与出行：最能体现跨 App、多业务证据融合。
2. 工作与商务：能训练模型识别会议、项目和任务之间的关联。
3. 电商与购物：能训练模型区分浏览兴趣、购买意向和实际交易。

**一个重要的实验提醒：** 这套 30 条事件、50% 无关行为的配置适合做第一轮固定条件实验，但不要把它当成最终真实用户分布。后续即使保持 6 小时窗口，也应该加入 10、20、50 条事件的密度对照，以及 30%、50%、70% 无关行为的噪声对照，避免模型只适应一种固定输入形态。

下一步可以把这份设计转成一套可执行的数据集生成规范：12 类场景的事件模板、统一 JSON Schema、标签校验规则和批量生成脚本。
